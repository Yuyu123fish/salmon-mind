# 开发流程

## 目的与责任

SalmonMind 是由开发者长期主导、多个 Agent 辅助开发的个人项目、作品集与求职项目。本流程用于保证每个增量真实可运行、范围可控、证据充分，并让开发者能够理解关键调用链和数据流。

- 开发者负责产品方向、关键取舍、阶段确认、实施授权和最终验收。
- Codex 负责仓库调研、问题诊断、领域与架构讨论、Spec / Plan、代码审查和验收辅助，也可以直接实现中小需求。
- Cursor、OpenCode 主要作为低成本代码执行器，按照完整交接提示完成修改和验证。

流程由开发者提出需求或明确要求继续下一阶段时触发。当前对话、仓库真实代码、已确认 Spec / Plan 和未提交工作区共同构成输入；任何 Agent 都不得把旧结论置于当前代码和开发者的新决定之上。

## 需求分级

需求按产品和架构影响分级，不按代码行数机械判断。存在高风险因素时自动提高等级。

| 等级 | 典型范围 | 默认路径 |
| --- | --- | --- |
| 小型 | 局部 Bug、样式、文案、小范围逻辑；不改变数据模型、公开接口或模块职责 | 明确问题 → 讨论方案 → 允许实施 → 验证 → 验收 |
| 中型 | 一个完整小 Feature、新接口、前后端闭环、数据库表或存储行为变化 | 调研 → Spec → Plan → 允许实施 → 验证 → 理解验收 |
| 大型 | 多个独立能力、跨模块重构、数据权威变化、复杂迁移或基础设施调整 | Feature Spec → 分 Stage Plan → 逐 Stage 实施与验收 |

中型需求可以合并 Spec 与 Plan 的讨论或确认；大 Feature 可以拆 Stage。是否合并、是否建分支和是否使用 PR 由当前风险决定，不固化成形式要求。

## 状态与授权

中大型 Feature 使用以下状态：

```text
Draft → Specified → Planned → Implementing → Implemented → Accepted
```

- `Draft`：问题和方案仍可调整。
- `Specified`：产品行为、领域语义、范围和验收标准已经确认。
- `Planned`：实施顺序、影响范围和验证方式已经确认。
- `Implementing`：开发者已经明确允许修改代码。
- `Implemented`：Agent 已完成修改和验证，等待开发者验收。
- `Accepted`：开发者已确认产品行为、代码理解和验证证据。

“可以”“够了”“方案没问题”默认只确认当前讨论或文档。只有“开始实现”“允许进入实施”“按这个方案直接开发”等明确表达才授权修改业务代码。实施、提交、推送和创建 PR 是四个独立动作，不能相互推断授权。

## 标准动作

### 1. 明确问题

Agent 首先只读检查仓库和相关运行事实：

1. 检查 Git 状态并识别已有修改。
2. 找到真实入口、调用链和当前约束。
3. 区分根因与表面症状。
4. 明确目标、非目标、需求等级和验收结果。

这一阶段不安装依赖、不修改代码、不写数据库迁移。若用户只要求诊断，输出原因和证据后停止。

### 2. 确认 Spec

中大型 Feature 在 `specs/features/NNN-feature-name/spec.md` 保存最终产品与技术合同。Spec 说明问题、用户行为、领域术语、状态与数据权威、失败和恢复行为、实施决定、测试决定、非目标与验收标准。

Spec 不承担实施流水账，也不使用容易过时的文件清单代替行为合同。开发者确认后才能标记为 `Specified`。

### 3. 确认 Plan

Plan 与 Spec 放在同一 Feature 目录，说明模块影响、实施顺序、迁移与兼容、验证方式、风险和停止条件。大 Feature 可以使用多个按顺序编号的 Stage Plan。

Plan 可以在实现中允许低风险细节动态调整，但不能授权 Agent 改变产品语义、数据权威、公开接口或 Feature 范围。

### 4. 实施

得到明确授权后，执行 Agent 必须：

1. 再次检查工作区，保护已有和无关修改。
2. 只修改本 Feature 范围内的文件。
3. 优先简单实现，不为未来能力增加空模块、假接口或通用框架。
4. 运行事先约定且与风险相称的验证。
5. 报告完成内容、调用链、数据流、验证证据、未验证范围和当前 Git 状态。

默认不提交、不推送、不创建 PR，也不自动进入下一个 Stage。

### 5. 验证与理解验收

小功能只做聚焦测试、构建或必要的手工检查，不堆叠重复测试。中大型功能的报告至少包括：

1. 完成的产品行为。
2. 修改的模块及其职责。
3. 入口、主要调用链和数据流。
4. 实际运行的命令、结果和环境。
5. 真实依赖验证范围与尚未验证的部分。
6. 已知限制和后续边界。

涉及模型 API、真实 Redis、RustFS、外部网络、费用或敏感凭据的验证必须先询问开发者。当前交付只要求本地可运行，不默认增加公开部署。

开发者从产品表现、技术理解和验证证据三个方面验收。验收后才把已成立能力同步为 `README.md` 和稳定 `docs/` 中的当前事实。

## Agent 交接与测试复用

交给执行 Agent 的提示词必须包含：当前检查点、精确范围、允许修改的区域、禁止事项、测试命令、报告格式和停止条件。执行 Agent 应自己运行约定测试并汇报结果，不能把验证留给接手者重复执行。

同一代码版本、同一环境和同一命令已经有可信结果时，后续 Agent 禁止重复运行。以下情况不视为重复，但必须说明新增验证的目的：

- 测试之后相关代码发生变化。
- 原报告缺少命令、结果或关键环境信息。
- 原测试没有覆盖当前验收目标。
- 需要不同层级的验证，例如单元测试之后进行真实页面或基础设施检查。

新增验证只覆盖缺口，不机械重跑全部命令。

## 偏差、失败与重试

- 普通实现错误由原执行 Agent 在已确认范围内修复，优先保留上下文，不随意更换 Agent。
- 产品语义、数据权威、公开接口、模块职责或范围发生变化时，立即停止并回到讨论；必要时更新 Spec / Plan 并重新授权。
- 测试失败先诊断原因，不通过反复重跑碰运气。
- 工作区存在重叠修改、迁移具有破坏性、凭据可能泄露或外部依赖需要新增权限时，停止并向开发者说明。
- 端口占用时使用明确的替代端口协调，不结束或修改未知进程。

## Git 与文档

- 小修改可以在当前开发分支完成。
- 中大型 Feature 默认使用一个 Feature 分支；多个 Stage 沿用该分支。
- 中小更新避免拆成大量提交；大型更新只在有独立验收价值时使用阶段提交。
- 提交前先让开发者检查变更范围；提交、推送和 PR 分别取得授权。
- 长期保留最终确认的 Spec、Plan、稳定文档和已验证的可复用规则。
- 临时提示词、Agent 草稿、工作日志和 Superpowers 过程文档不得进入提交。

## 成功证据

一次开发增量只有同时满足以下条件，才可以进入 `Accepted`：

- 产品行为符合已确认 Spec。
- 实现范围没有暗中扩大。
- 测试与真实验证和风险相称，结果可追溯且没有重复浪费。
- 开发者能够获得清晰的入口、调用链、数据流和失败路径说明。
- 未验证范围和已知限制被明确报告。
- Git 和稳定文档的后续动作仍由开发者决定。
