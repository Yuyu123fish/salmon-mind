# Feature 003 功能报告：本地文档 RAG 与双网页搜索

Status: Accepted

Accepted on: 2026-08-18

## 1. 最终结果

SalmonMind 现在具备了一个以本地文档为核心、可以结合网页信息和模型已有知识的多轮问答闭环。

用户可以上传 TXT、Markdown、PDF 和 DOCX 文档，在 Knowledge 页面查看处理状态、解析结果、切片和召回过程；文档可用后，聊天 Agent 可以主动检索本地知识库，也可以在用户允许联网时选择博查或 SearchApi.io。回答中真正使用的来源会显示为可追溯的本地或网页引用，刷新和继续对话后仍然存在。

这次 Feature 同时收口了两个 Conversation 问题：新对话只有在首次发送非空消息时才会创建；成功回答的持久化与 SSE 传输被明确分开，客户端断流不会把已经成功的 Run 改回失败。

## 2. 新增能力

### 2.1 本地知识库

- 支持上传 TXT、Markdown、PDF 和 DOCX，接收阶段会校验格式、大小和文件内容，不把伪装格式当作正常文档。
- 文档接收后立即进入异步处理，上传请求不等待解析、嵌入和索引完成。
- Knowledge 页面可以查看文档状态、当前处理阶段、解析元数据、失败原因、处理尝试和 Evidence 预览。
- 支持对可恢复失败执行重试；扫描 PDF 会明确进入 `OCR_REQUIRED`，不会被误报为解析成功。
- 原始文档、业务状态和搜索索引分别由适合它们的存储承担，索引损坏时仍可以从原件和业务元数据重建。

### 2.2 可解释的混合检索

- 文档内容经过 Apache Tika 解析和有界切片，再使用 `Qwen/Qwen3-Embedding-4B` 生成 2560 维向量。
- 查询同时进行关键词召回和向量召回，两路结果通过 RRF 按排名融合，不直接混加无法比较的原始分数。
- 融合候选再交给 `Qwen/Qwen3-Reranker-4B` 精排，最终只把有界 Evidence 交给 Agent。
- 诊断界面可以看到关键词、向量、RRF 和精排各阶段的顺序与分数，方便判断答案为什么命中某份文档。
- 向量或精排服务不可用时会明确标记降级，不把关键词兜底伪装成完整混合检索。

### 2.3 Agent RAG 与网页搜索

- Agent 拥有三个只读工具：本地知识检索、博查网页搜索和 SearchApi.io 网页搜索。
- 涉及用户文档时优先查询本地知识；涉及新闻、版本、政策等时效信息时，可以在用户允许联网的前提下选择网页工具。
- 中文或中国互联网信息默认倾向博查，明确要求 Google、国际网页或英文检索时倾向 SearchApi.io；首个提供方为空或不可用时，可以在预算内尝试另一个。
- 同一个问题可以组合本地文档和网页现状。普通稳定知识、创作问题或检索无结果时，仍允许使用模型知识回答。
- 模型知识、本地文档和网页结果具有明确的措辞与引用边界；没有来源时不会生成虚假来源卡片。

### 2.4 可验证引用与多轮上下文

- 每次工具运行只为当前 Run 分配短引用编号，本地来源使用 `L`，网页来源使用 `W`。
- 最终回答完成时，系统会核对正文中的引用是否真的来自本 Run 的工具结果。模型虚构或从旧轮次复制的编号不会变成可点击 Citation。
- Assistant 历史保存最小结构化引用。本地引用包含文档和位置，网页引用包含提供方、标题、URL、站点和检索时间；原始大块工具结果不会长期保存。
- 下一轮可以看到上一轮回答及有界来源摘要，从而理解之前依据了什么；若需要重新核验原文或实时信息，Agent 必须再次检索，不能把历史编号当作当前证据。
- 对话压缩会保留“结论来自本地、网页还是模型知识”的边界，同时避免把旧引用升级成本轮 Citation。

### 2.5 上下文与运行安全边界

- 主调用预算现在同时考虑系统提示、实际工具定义、JSONL 历史投影、历史引用摘要、当前轮工具结果和回答输出预留。
- 每个 Run 的工具结果总预算默认是 32,768 token，最多调用工具 4 次；结果超限时按完整 Evidence 或网页结果裁剪，不产生半截 JSON 或失效引用。
- Agent Loop 默认最多进行 32 次模型调用，预算耗尽或模型反复调用工具时能够有界结束。
- 工具启用后，每轮都从 JSONL Active Path 重建模型上下文。Redis Checkpoint 只负责运行加速，不会成为一份比 JSONL 更丰富、但重启后无法恢复的隐藏历史。

## 3. 实际处理流程

### 3.1 文档进入知识库

1. Server 对上传文件进行同步校验，把原件写入 RustFS，并在 PostgreSQL 记录文档、版本和处理状态。
2. 任务写入 Redis Stream 后，HTTP 立即返回异步状态。PostgreSQL 不承担高频队列轮询，因此不会为大量出入队制造额外 WAL 压力。
3. Server 内的有界后台线程通过 Consumer Group 获取任务，使用 Tika 解析正文和基础元数据。
4. 正文按稳定规则切成带位置描述的 Evidence，再批量生成 2560 维向量并写入 Elasticsearch。
5. 只有整份文档的 Evidence 都完成校验和索引发布后，该版本才进入 READY；部分写入或处理中断的内容不会参与检索。
6. Redis 暂时不可用、消息重复投递或 Worker 中断时，系统可以根据 PostgreSQL 状态和处理记录重新分发、认领或重试，避免重复 Evidence。

### 3.2 一次本地检索

1. 查询先限定在当前 Workspace、当前有效索引代次以及 PostgreSQL 已确认 READY 的文档版本。
2. Elasticsearch 分别返回关键词候选和向量候选。
3. 应用层只根据两路排名执行 RRF 融合和去重，再选取有限候选进行精排。
4. 最终 Evidence 携带稳定身份、文档名、位置和有界正文进入 Agent；向量、内部索引名和存储地址不会暴露给前端或模型回答。

### 3.3 一次 RAG 问答

1. 用户消息先作为 durable Entry 写入 Conversation 历史，再启动本轮 Run。
2. 主模型根据用户意图决定不使用工具、查询本地、查询一个网页提供方，或顺序组合多个来源。
3. 每个工具结果在返回模型前完成大小控制、来源登记和不可信内容隔离。
4. 模型生成最终回答后，系统只接受能映射到本轮真实来源的引用，并把回答与结构化 Citation 一起写入 JSONL。
5. PostgreSQL 用一个短事务完成 Run 成功状态和 Conversation 活动叶子的推进；事务提交后才发送最终 SSE 事件。
6. 如果成功提交后的网络连接中断，客户端刷新时会从 JSONL 和数据库恢复已经成功的回答，而不会把 Run 降级为失败。

### 3.4 后续轮次与长对话

每轮开始前，系统从当前 Active Path 构造可恢复上下文。历史 Assistant 的正文和来源摘要进入模型，但上一轮原始工具结果不会跟随 Redis Checkpoint 混入新一轮。

当预计输入接近工作窗口时，系统在调用主模型前先压缩较早历史，保留近期完整交互和结构化摘要。压缩前后使用同一套来源渲染和预算口径，因此不会出现“模型看见了引用、预算却没有计算”的偏差。压缩后仍然过长时会明确结束，而不是无限重试。

## 4. 关键困难与解决方式

### 4.1 多种存储之间不能假装存在全局事务

原件、业务状态、队列、索引、Conversation 历史和 SSE 分布在不同系统中。若用一个长数据库事务包住模型、工具或网络传输，不仅无法真正原子化，还会长时间占用连接。

最终采用“明确权威 + 可恢复顺序”：原件和 JSONL 保存不可替代事实，PostgreSQL 保存业务状态与修复指针，Redis/Elasticsearch 保存可重建状态；每一步失败后都能知道应以哪一处为准恢复。

### 4.2 异步队列既要减轻数据库压力，也要承受重复投递

Redis Stream 解决了高频队列读写对 PostgreSQL WAL 和用户请求的干扰，但 Consumer Group 提供的是至少一次处理语义。为此，文档版本、处理任务、Evidence 和索引代次都使用稳定身份与状态约束；重复消息会覆盖或复用同一结果，而不是产生第二套文档切片。

### 4.3 关键词分数和向量分数无法直接比较

两种召回的原始分数含义不同，直接加权容易制造看似精确、实际无法解释的结果。本 Feature 采用基于名次的 RRF 融合，再由统一精排模型判断候选与问题的相关性，同时在诊断界面保留每一阶段的来源和排名。

### 4.4 引用必须来自真实工具结果

仅靠解析模型生成的 URL 或文档名无法阻止幻觉。系统因此在当前 Run 内先登记工具返回的真实来源，再从最终回答中反向核对引用编号；不存在、已经被裁剪或属于旧 Run 的编号都不会形成结构化 Citation。

### 4.5 原始工具结果不持久化，但多轮对话仍要理解来源

保存完整工具结果会快速放大 JSONL 和上下文，也会让 Redis Checkpoint 变成隐藏历史；完全丢弃又会让下一轮不知道之前依据了什么。

最终只长期保存最小 Citation，并在投影时生成有界历史来源摘要。这样后续轮次能理解上轮依据，同时真正需要证据时仍会重新检索，避免把过期网页或旧编号当作当前事实。

### 4.6 工具加入后，上下文预算不再只是聊天正文

系统提示、三个工具的 schema、工具调用参数和结果都会消耗上下文。只计算历史正文会在长对话中低估输入，单次结果字符限制也无法约束四次工具调用的累计大小。

当前预算把静态工具开销和每 Run 动态结果统一纳入压缩判断，并同时设置结果总预算、调用次数和 Agent Loop 上限。来源型结果只按完整条目裁剪，使上下文安全与 Citation 正确性使用同一个边界。

## 5. 最终效果

对用户而言，SalmonMind 已从普通聊天扩展成可管理、可解释、可追溯的个人文档问答系统：

- 上传文档后可以看到它是否正在排队、解析、嵌入、索引、可用或失败；
- 可以直接检查知识库为什么召回某段内容，而不是把检索过程当作黑盒；
- 可以在同一问题中结合自己的资料和外部最新信息；
- 每个真实来源都能在回答下方定位或打开，刷新后不会消失；
- 检索失败或没有依据时，对话仍能继续，但回答会明确区分模型知识与已验证来源；
- 长对话、Redis Checkpoint 丢失和成功后 SSE 断流不会破坏 durable Conversation 语义；
- 点击“新对话”但不发送内容，不再产生无意义的服务端会话。

对维护者而言，文档原件、业务状态、异步队列、可重建索引、Conversation 历史和临时 Agent 状态已经有清晰权威边界。外部模型、Redis、RustFS、Elasticsearch 或网页搜索未配置时，应用仍可启动，只有实际使用对应能力时才返回稳定错误。

## 6. 验收证据与边界

当前最终代码版本留下的自动化报告包含 24 个后端测试套件、96 项测试，失败与错误均为 0；覆盖模块边界、Conversation 持久化与恢复、Agent 工具循环、上下文预算、异步 Knowledge 流程、混合检索、双网页适配和 Citation 兼容。前端生产构建产物也已生成。

开发者已在 2026-08-18 将 Feature 003 的 Spec 与五个 Stage Plan 最终确认为 `Accepted`。

本报告不把没有证据的真实付费外部调用写成已完成事实。SiliconFlow、博查、SearchApi.io 和真实 Chat 模型在具体部署中的可用性仍取决于凭据、套餐、网络和提供方合同；本次接受将这部分视为环境相关 Smoke 边界，而不是自动化验证已经覆盖的事实。

## 7. 当前限制

- 不支持 OCR；扫描 PDF 只能识别为需要 OCR，不能提取其中图片文字。
- 不索引本地代码项目、Git 仓库或目录，不监听文件变化。
- 不抓取网页全文，不把 URL、网页搜索结果或网络笔记写入本地知识库。
- 不支持文档删除、替换版本、批量目录上传、标签、权限或多人共享。
- 不包含模拟面试、项目审查、能力评估等上层 RAG 业务。
- 不包含登录、多用户、远程访问和公开部署。

这些限制是 Feature 003 的明确边界，不代表当前链路中的未完成步骤。
